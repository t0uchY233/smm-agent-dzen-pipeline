# Маршрут публикации в Дзен

Контракт выпуска: `docs/specs/content-release.md`. Исполняющий навык: `.agents/skills/dzen/SKILL.md`. Основной путь — общий CLI `tools/publish_release.py`, адаптер `tools/publishing_dzen.py` и Playwright/CDP-транспорт `dzen-publish/`. Происхождение и лицензионное ограничение: `dzen-publish/UPSTREAM.md`.

## До утверждения: только локальный комплект

1. Прочитать DOCX через `tools/read_docx.py`, проверить журнал, старое и текущее состояние выпуска. Существующий объект не дублировать. Запрос только Дзена не разрешает изменения других площадок.
2. Подготовить заголовок, статью, локальные изображения, точный канал и будущее время. Явная дата пользователя приоритетнее имени файла; по умолчанию Europe/Moscow, запас минимум минута. Прошедшее время не заменять немедленной публикацией.
3. Для DOCX с изображениями извлечь `dzen_sequence_path` через `tools/extract_docx_dzen_sequence.py`. Сохранить единый порядок «абзац → изображение → следующий абзац». Текст sequence должен совпадать с `dzen_article`, изображения и их контекст — с DOCX. Не передавать эти картинки отдельным `dzen_images`.
4. Завершить статью ровно одним блоком из `.agents/skills/dzen/references/required-footer.md`. Он входит в утверждаемую версию; проверить пять активных ссылок в предпросмотре редактора перед отправкой. Изображения `.png`, `.jpg`, `.jpeg`, `.bmp`, `.webp`, `.gif` должны существовать и открываться локально.
5. Выполнить `tools/publish_release.py prepare --manifest <json>` и `tools/publish_release.py status --release <dir>`. Показать материалы, файлы, канал, московскую дату и revision. После OK именно этой версии — `tools/publish_release.py approve --release <dir> --revision <hash>`. Уже утверждённую неизменную версию не пересогласовывать.

## После утверждения: черновик и назначение

Подключение описано в `.agents/skills/dzen/references/cdp-recovery.md`: Linux использует `tools/chrome_cdp.py`, Windows — `dzen-publish/ensure_cdp_chrome.ps1`. Режим `DZEN_CDP_MODE=external` использует существующий loopback CDP без локального запуска Chrome. Локальный Chrome от root запрещён. Авторизация хранится в выбранном профиле; cookies и токены не передаются через чат.

`dzen-publish/publish_dzen.py --healthcheck` — диагностика подключения без редактора, не проверка авторизации. Адаптер ограниченно восстанавливает CDP до редактора и отдельно проверяет права целевого канала. Ограничение Browser-инструмента не означает недоступность Дзена; сначала проверить основной CDP-путь.

```text
python tools/publish_release.py prepare-dzen --release <dir>
python tools/publish_release.py schedule-dzen --release <dir>
python tools/publish_release.py check-dzen --release <dir>
```

`prepare-dzen` уже создаёт внешний черновик, поэтому до утверждения запрещён. schedule-dzen использует его и сверяет содержимое; без отдельного prepare-dzen он может создать черновик сам. Не запускать две независимые цепочки для одного выпуска.

Windows с Word допускает единую rich-вставку через `tools/copy_docx_body_to_clipboard.ps1` внутри адаптера. Linux и Windows без Word используют sequence. Поле `dzen_docx_mode=sequence` выбирается до утверждения. Не вызывать старые самостоятельные параметры статьи для обхода manifest/revision.

Перед отправкой транспорт сверяет заголовок, полный текст, пять ссылок, число изображений, ненулевые naturalWidth/naturalHeight и контекст до/после каждого изображения. Повторно проверяет revision и запас времени, затем один раз назначает публикацию.

## Независимая проверка и сбои

check-dzen запускается отдельно и требует неизменной утверждённой revision. Подтверждение отложки: уникальная строка очереди, идентичность объекта, целевой канал, точные дата и время МСК, текст, изображения и ссылки авторского превью. Различия представления пробелов, дат и соседних абзацев не отменяют проверку содержимого и границ изображений. Сохраняются `dzen-observation.json`, состояние выпуска и подтверждённые события журнала.

Первый read-only запуск после изменений разметки обязателен: наличие локальных тестов не доказывает работу текущего сайта. URL `/a/…`, клик или `prepared` не подтверждают отложку. Будущий срок — «Запланировано». Текущее observe не подтверждает публичный выход после срока полноценно: исчезновение из очереди оставляет результат неподтверждённым до независимой сверки, а не означает успех.

При ошибке инструмента или неопределённом результате остановить внешние изменения: status/check-dzen, сверка существующего объекта и точный блокер. Не очищать `draft_attempted`, `attempted`, ID или журнал. При неизвестном draft_url нет отдельной команды привязки — найти объект и сообщить ограничение, не создавать дубль. Первый таймаут подключения сам по себе не означает `failed`.

Browser Use/Computer Use — только доступный резерв после конкретного сбоя CDP, для того же объекта. `tools/publish_release.py record-browser --release <dir> --platform dzen --evidence <json>` сохраняет наблюдение, но не публикует и не делает его автоматически достоверным. Если сверка или авторизация недоступны, сохранить комплект и сообщить блокер. Успехи других площадок не стирать.

Общий CLI пока не поддерживает немедленный выпуск, перенос/отмену расписания и привязку потерянного черновика. Не заменять эти запросы другой операцией без согласования.
