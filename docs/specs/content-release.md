# Выпуск через Codex без n8n

Статус: реализован локальный CLI; внешняя приёмка требует авторизации и согласованного тестового выпуска. Наличие кода и unit-тестов не подтверждает публикации на реальных площадках.

## 1. Исходное состояние

Присланный SOP описывал сценарий → запись → монтаж → Drive → n8n → YouTube → согласование Telegram и Дзена → автоматический выпуск. В репозитории README, RECIPE и действующие навыки уже описывали прямую загрузку только YouTube. Сохранённые n8n JSON содержали YouTube uploader и Telegram/WordPress publisher; отдельного опубликованного и проверенного пути Дзена не было.

| Given | When | Then по старому SOP |
|---|---|---|
| Тема | Пользователь обращается к Codex | Уточнение даты и кейса, сводка |
| Сводка | OK | Текст суфлёра и DOCX |
| DOCX | Пользователь записывает видео | Raw MP4 |
| Raw MP4 + DOCX | Монтаж | Rendered MP4 |
| Rendered MP4 | Загрузка в Drive | n8n загружает YouTube и присылает ссылку |
| YouTube URL | `/publish-from-script` | Превью Telegram и статьи |
| Превью | OK и наступление срока | Публикации и уведомление |

Новая цепочка полностью исключает n8n, Drive, Sheets, WordPress и блог veselkov, в том числе хранение изображений и RSS. Исторические интеграции в рабочую поставку не входят.

## 2. Целевой контракт

### Ответственность и SOP

1. Пользователь задаёт тему, материалы и будущее время по Москве.
2. Codex показывает сводку; после OK создаёт текст и DOCX со встроенными изображениями. Выдуманный кейс обозначается как условный.
3. Пользователь записывает видео. Codex монтирует его по DOCX и проверяет кадры, все визуалы, непрерывный PiP, звук и длительность.
4. Codex читает DOCX через `tools/read_docx.py`, создаёт описание и локальную обложку YouTube, видео с текстом Telegram и статью Дзена. Тексты проходят tone-of-voice → ru-text → slop-stop. Показывается общий комплект, каналы и дата.
5. После утверждения текущей версии Codex загружает YouTube, получает URL, подставляет его вместо `{youtube_url}`, назначает Telegram и Дзен. Подстановка этой ссылки входит в утверждение и не требует повторного OK. Иные правки материалов требуют нового утверждения.
6. Codex проверяет серверные состояния и сообщает результат по каждой площадке. Отключение компьютера после подтверждённой постановки не отменяет серверное расписание.

Команды: `/video-script`, `/render-docx-visuals "<raw_mp4>" --docx "<docx_path>"`, `/publish-from-script "<rendered_mp4>" --docx "<docx_path>"`. Последняя по умолчанию готовит три площадки; явно ограниченный запрос выполняется только для выбранных. YouTube URL означает существующий ролик: без автоматической перезагрузки или изменения опубликованного материала.

### Транспорты и происхождение

Общий CLI сохраняет утверждение, защиту от дублей и состояние выпуска; вендорные транспорты не запускаются в обход этих проверок.

| Площадка | Upstream | Commit | Адаптер | Происхождение |
|---|---|---|---|---|
| YouTube | https://github.com/hassancs91/claude-youtube-editor | `a6ac742b44520fd3c6aeaf3cd754e113fa334fed` | `tools/publishing_youtube.py` | `youtube-publish/UPSTREAM.md` |
| Telegram | https://github.com/chigwell/telegram-mcp | `0246df8c3c99818d68f50e8591b2d3dda8363f81` | `tools/publishing_telegram.py` | `telegram-publish/UPSTREAM.md` |
| Дзен | https://github.com/Andrrreyiv/dzen-publish | `a6bbc78b151523a195c21570f14985b3f2615d29` | `tools/publishing_dzen.py` | `dzen-publish/UPSTREAM.md` |

YouTube использует validate/build_body/preview из `youtube-publish/yt_upload.py`; OAuth, загрузка и состояние остаются проектными. Telegram использует извлечённые функции `telegram-publish/tg_post.py`, не запускает MCP runtime. Дзен использует локально расширенный Playwright/CDP-транспорт `dzen-publish/publish_dzen.py`.

Ограничения: неаудированный YouTube API-проект может принудительно оставлять ролики private; `publishAt` не доказывает публичный выход. В обзоре Telegram upstream Telethon отмечен как архивный, без установленной даты архивации; переход на другую библиотеку требует отдельной проверки сессий и отложки. У upstream Дзена нет лицензии (проверка 2026-11-02): права на копирование не подтверждены, запрос автору ещё не отправлялся. Подробности и локальные изменения — в трёх UPSTREAM.md.

### Подключения

Установить Python-зависимости: `python -m pip install -r requirements-publishing.txt`. FFmpeg/ffprobe нужны для проверки монтажа. Настройки перечислены в `.env.example`; заполнить локальный `.env`, не выводить его в чат.

- Telegram: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` из https://my.telegram.org, `TELEGRAM_CHANNEL_ID` (рекомендуется числовой `-100…`), `TELEGRAM_SESSION_PATH=.local/auth/telegram.session`. `python tools/publish_release.py auth-telegram` запускается пользователем в локальном терминале; телефон, код и пароль вводятся интерактивно, не через чат. Нужен пользовательский аккаунт с правом публикации в канале, не BotFather. `TELEGRAM_ALLOWED_CHAT_IDS` — дополнительный список разрешённых получателей (числовые ID через запятую); пустое или отсутствующее значение отключает только этот дополнительный фильтр. Проверки утверждения, `TELEGRAM_CHANNEL_ID`, типа канала и прав сохраняются. При заданном списке разрешение проверяется до загрузки файла. Агент не расширяет и не отключает список ради отправки.
- YouTube: включить Data API v3, создать OAuth Web application, задать `YOUTUBE_CLIENT_ID`, `YOUTUBE_CLIENT_SECRET`, `YOUTUBE_CHANNEL_ID` в `.env`. В Authorized redirect URIs добавить в точности `http://localhost:8765/`, включая завершающий слеш; Authorized JavaScript origins не нужны. Команда `python tools/publish_release.py auth-youtube` временно запускает локальный callback-сервер и открывает OAuth-вход. Порт 8765 должен быть свободен; при конфликте он не заменяется случайным портом. Токены сохраняются автоматически в `YOUTUBE_TOKEN_PATH=.local/auth/youtube-token.json`. Пара ID/Secret имеет приоритет над JSON; неполная пара вызывает ошибку. При смене клиента повторить авторизацию. Резервный вариант: если оба поля пусты, OAuth Desktop JSON читается из `YOUTUBE_CLIENT_SECRETS_PATH=.local/auth/youtube-client.json`. Используются scopes youtube.force-ssl (в том числе videos.update для назначения времени) и youtube.readonly.
- Дзен: авторизованный Chrome CDP, точный URL редактора целевого канала в manifest. Linux: `tools/chrome_cdp.py`; Windows: `dzen-publish/ensure_cdp_chrome.ps1`. `DZEN_CDP_MODE=external` использует существующий loopback CDP без локального запуска Chrome. `DZEN_CDP_URL`, `DZEN_CHROME_PROFILE`, `CHROME_BINARY` задают подключение. Публикация идёт через общий CLI, а не старые самостоятельные параметры статьи. Подключение CDP не доказывает вход; адаптер проверяет права перед изменениями. См. `.agents/skills/dzen/references/cdp-recovery.md`.
- `PUBLISH_TIMEZONE=Europe/Moscow`. Секреты, токены и сессии хранятся вне Git. Встроенной генерации изображений ключ API не нужен.

### Комплект и состояние

DOCX и MP4: `YYYY-MM-DD-HHMM-Русский заголовок` с разными расширениями. Источник текста — DOCX; готовый MP4 — из `.tmp/rendered/`. Явное время пользователя приоритетнее имени. Если оно не задано, Codex извлекает его через `read_docx.py`; CLI получает уже разрешённое значение. Если осталось меньше минуты, согласовать новую дату; никогда не подставлять прошедшее время в API.

Каталог `.tmp/publishing/<docx-base>/` содержит `manifest.json`, `state.json`, `events.jsonl`, разрешённые тексты `.tmp/publishing/<docx-base>/telegram.txt` и `.tmp/publishing/<docx-base>/dzen.md`, браузерные доказательства. Этот каталог является рабочим журналом и не подлежит автоматической очистке. Проверить старый `.tmp/youtube/<docx-base>/upload-state.json`, `publish-log.md` и канал до новой загрузки.

Минимальный manifest (пути относительно корня проекта; разрешены абсолютные локальные пути):

```json
{
  "docx_path": ".tmp/teleprompter/2030-01-20-1400-Тема.docx",
  "video_path": ".tmp/rendered/2030-01-20-1400-Тема.mp4",
  "render_report_path": ".tmp/rendered/2030-01-20-1400-Тема.qa.json",
  "thumbnail_path": ".tmp/covers/Тема.png",
  "title": "Тема",
  "description": "Утверждённое описание из DOCX",
  "made_for_kids": false,
  "youtube_category": "28",
  "scheduled_at": "2030-01-20 14:00",
  "timezone": "Europe/Moscow",
  "platforms": ["youtube", "telegram", "dzen"],
  "youtube_channel": "UC_CHANNEL_ID",
  "telegram_channel": "-1001234567890",
  "dzen_channel": "https://dzen.ru/profile/editor/CHANNEL",
  "telegram_text": "Утверждённый текст\n{youtube_url}",
  "dzen_article": "Утверждённая статья\n{youtube_url}",
  "dzen_images": []
}
```

`dzen_article` в примере — сокращённый шаблон, не готовая статья. До `prepare` добавь к полному тексту ровно один полный обязательный футер из `.agents/skills/dzen/references/required-footer.md`; если он уже есть в конце статьи, не добавляй второй. Замени `CHANNEL` точным идентификатором редактора своего канала.

`youtube_category` необязательна: пример `28` не рекомендация для всех выпусков. Если поле отсутствует, адаптер не отправляет categoryId; значение по умолчанию вендора не подставляется.

Для DOCX со встроенными изображениями обязателен `dzen_sequence_path` — путь к JSON из `tools/extract_docx_dzen_sequence.py`. Формат: `{"title": "Тема", "blocks": [{"type": "text", "text": "Абзац"}, {"type": "image", "path": "локальный-файл.png"}]}`. Заголовок и текст должны совпадать с manifest; число, порядок и содержимое изображений и контекст — с DOCX. В конце один обязательный footer из `.agents/skills/dzen/references/required-footer.md`; его файл, sequence и все изображения входят в revision. При sequence поле `dzen_images` должно быть пустым; оно предназначено для независимых вложений, не для картинок DOCX. `dzen_docx_mode` допускает `auto` (по умолчанию), `word` или `sequence`; режим выбирается до утверждения. На Linux используется sequence, на Windows с Word возможна единая rich-вставка. Приведённый manifest без sequence подходит только DOCX без изображений.

Для существующего ролика добавить `youtube_id`. Если выбраны только Telegram/Дзен, указать ID уже проверенного ролика для ссылки. `made_for_kids` определяется содержанием, пример `false` не является универсальным значением.

Отчёт QA готовит агент по результатам монтажа; он должен фиксировать присутствие всех визуалов, PiP, звук и длительность, а не содержать неподтверждённое «OK». SHA-256 утверждения охватывает manifest и содержимое всех перечисленных файлов. Новая версия не переписывает уже назначенные серверные публикации: сначала сверить их и согласовать изменение отдельно.

CLI:

```text
python tools/publish_release.py prepare --manifest <prepared-json>
python tools/publish_release.py status --release <release-dir>
python tools/publish_release.py preview-youtube --release <release-dir>
# Показать комплект и получить утверждение конкретной revision.
python tools/publish_release.py approve --release <release-dir> --revision <hash-from-preview>
python tools/publish_release.py schedule-youtube --release <release-dir>
python tools/publish_release.py render-texts --release <release-dir>
python tools/publish_release.py schedule-telegram --release <release-dir>
python tools/publish_release.py prepare-dzen --release <release-dir>
python tools/publish_release.py schedule-dzen --release <release-dir>
# Независимая сверка отдельными запусками.
python tools/publish_release.py check-youtube --release <release-dir>
python tools/publish_release.py check-telegram --release <release-dir>
python tools/publish_release.py check-dzen --release <release-dir>
```

Это порядок действий, не команда для безусловного запуска всех площадок. `prepare` локален, но требует будущей даты и валидных файлов. Для существующего каталога он завершится ошибкой: продолжать надо из сохранённого состояния. `status` показывает revision и локальное состояние, не проверяет сервер. `preview-youtube` работает офлайн, без загрузки `.env` и OAuth; допустим только для новой загрузки YouTube. Для существующего ID пропустить preview/schedule YouTube и выполнить `check-youtube` при заданном целевом канале. Если выбраны только Telegram/Дзен, ID сначала независимо сверяется и сохраняется для ссылки.

`prepare-dzen` создаёт внешний черновик и требует утверждения, как и `schedule-dzen`. До OK допустимы только локальные материалы и read-only диагностика. schedule-dzen умеет создать черновик сам, но маршрут выше отделяет его проверку от отправки. В check-dzen тоже проверяется утверждённая revision: при изменении локальных файлов не обходить защиту, а сообщить блокер.

`approve` запускается агентом только после OK соответствующего превью или уже данного явного утверждения этой версии. Само поручение реализовать инструменты не утверждает конкретный выпуск.

Статусы отдельно по площадкам: `prepared`, `uploaded`, `scheduled`, `published`, `failed`. Технические состояния `uploading`, `sending`, `unconfirmed` означают незавершённую сверку. Ошибка не стирает известные ID. Блокировка `.lock` исключает параллельную работу с одним выпуском; после аварии её удаляют только после проверки процесса.

### YouTube

Проверить OAuth-канал, загрузить приватно, сохранить ID сразу после ответа, установить thumbnail, повторно проверить время и назначить `publishAt`. Прочитать результат через API, отдельно сообщить состояние обработки. Повторный запуск проверяет известный ID; после неопределённого upload без ID новая загрузка блокируется. Искать ролик в Studio по названию и тегу `codex-release-<release_id>`, затем записать наблюдение через `record-browser`.

API-проекты могут быть ограничены приватными загрузками до аудита. Успешный HTTP-ответ сам по себе не доказывает доступность публичного выпуска: проверить расписание и ограничения в Studio при первой настройке проекта. При ограничении продолжить через Studio с существующим роликом, не загружая копию вслепую. Автоматического обхода ограничений нет.

### Telegram

Адаптер с транспортом telegram-mcp использует пользовательскую MTProto-сессию Telethon. Проверить канал и право post_messages, загрузить файл, затем повторно проверить запас времени и передать серверную дату. Получить список отложенных сообщений и сверить ID, содержание, медиа и дату. Длинный текст делится по лимитам сервера: у видео короткая подпись с URL, остальные части — отдельные сообщения на то же время; атомарность и порядок отдельных сообщений не гарантируются.

После таймаута без ID или FloodWait не повторять отправку автоматически и не ждать ради автоматического повтора. Клиент отключает повторные запросы и автоматический sleep; attempted-часть без ID сохраняется для сверки. Сначала осмотреть отложку. Для найденной части выполнить `reconcile-telegram --release <dir> --part-index <индекс-с-нуля> --message-id <ID-в-отложке>`: CLI сверяет канал, текст, дату и параметры медиа перед привязкой. Идентичность видео дополнительно проверить визуально; размер файла не доказывает совпадение содержимого. Если объект не найден, не сбрасывать попытку без ручной проверки канала. Исчезновение сообщения из очереди не означает публикацию: оно могло быть удалено. При поздней проверке CLI ищет уникальное совпадение текста/медиа в последних 200 сообщениях и временном окне 0–5 минут после срока; за пределами этой выборки требуется браузерная сверка. При неоднозначности сохранить `unconfirmed`. Превышение размера видео блокирует отправку и требует согласования отдельной Telegram-версии, не скрытой замены ссылкой.

### Дзен и CDP-подтверждения

Прочитать `.agents/skills/dzen/SKILL.md` и `docs/dzen-publication-route.md`. После локальной подготовки и утверждения: prepare-dzen → schedule-dzen → отдельный check-dzen. Адаптер вызывает `tools/chrome_cdp.py`, ограниченно восстанавливает подключение до открытия редактора и проверяет права на целевой канал. Read-only `dzen-publish/publish_dzen.py --healthcheck` доступен для диагностики, но не доказывает вход. Linux требует desktop/Xvfb и запрещает локальный запуск Chrome от root; external не запускает Chrome. Не обходить ограничения настройками безопасности.

До отправки проверяются полный текст, ссылки, число и ненулевые размеры изображений, порядок и контекст каждого блока; запас времени и revision проверяются ещё раз после вставки. `draft_attempted` сохраняется до создания черновика, `attempted` — до назначения. Не сбрасывать флаги при сбое. При известном draft_url сверять тот же объект; при неизвестном URL сначала найти существующий черновик, не создавать новый.

Независимое наблюдение читает очередь и авторское превью: уникальный объект, канал, точное время МСК, полный текст, изображения и активные ссылки. Разница обычных/неразрывных пробелов и представления даты допускается только при сохранении смысла и идентичности объекта. URL `/a/…` до срока может вести на авторское превью; гостевой 404 не доказывает сбой. Локальные тесты не подтверждают текущую разметку: первый запуск после её изменений требует read-only сверки существующего утверждённого выпуска.

Текущее CDP observe подтверждает будущую очередь, но не реализует полноценное подтверждение публичного выхода после срока; check-dzen может оставить `unconfirmed`. Исчезновение из очереди не равно публикации. Нет CLI-команд для привязки потерянного draft_url, отмены/переноса расписания или немедленного выпуска. Также нет отдельной команды загрузки YouTube только private без будущего времени. При таком запросе сохранить подготовку и сообщить ограничение, не выдумывать команду и не менять смысл поручения.

Browser/Studio — резерв после наблюдаемого сбоя основного API/CDP для сверки и восстановления существующего объекта. При недоступности инструментов или авторизации сохранить комплект и конкретный блокер. Не запускать резервную отправку вслепую.

`record-browser --release <dir> --platform dzen|youtube --evidence <json>` фиксирует наблюдение, но не выполняет браузерное действие и не подтверждает его автоматически. Поля JSON: `url`, `channel`, `status`, `observed_at` (ISO с часовым поясом), `evidence_path`, для scheduled — `scheduled_at`, для YouTube — `id`. Канал и срок должны совпадать с комплектом. Публикация Дзен не зависит от WordPress, RSS или публичного хранилища обложек.

Политика сбоя: при неопределённом результате или ошибке инструмента остановить внешние изменения, выполнить доступные `status`/`check-*` и сверку существующего объекта, затем сообщить блокер. Если сама сверка недоступна, сохранить неопределённость. Не повторять отправку и не очищать состояние ради повтора. Ограниченные повторы чанка внутри одного resumable-запроса YouTube не разрешают агенту новый insert или повторный запуск отправки.

Итог — подтверждённая отложка по каждой выбранной площадке. Если одна не завершена, остальные не откатывать и не дублировать. Фактический выход проверяется отдельным запуском; постоянный монитор и автоматическое уведомление после выхода в эту версию не входят.

## 3. Приёмка Given / When / Then

| ID | Given | When | Then |
|---|---|---|---|
| S01 | Тема, будущая дата | OK сценария | DOCX, визуалы и обозначенные условные кейсы |
| S02 | Raw и DOCX | Монтаж | Все визуалы, непрерывный PiP, проверенные звук и длительность |
| S03 | Готовый комплект | Запрос выпуска | Общее превью каналов, материалов и времени |
| S04 | Нет утверждения или файлы изменены | Попытка публикации | Сетевые изменения блокируются |
| S05 | Утверждённый комплект | Загрузка YouTube | ID, URL, thumbnail, проверенные расписание и обработка |
| S06 | Ограниченный API-проект | Планирование | Studio с проверкой существующего ролика |
| S07 | URL и Telegram-материалы | Планирование | Все сообщения в серверной отложке правильного канала |
| S08 | Длинный текст | Подготовка Telegram | Короткая подпись и дополнительные сообщения в пределах лимитов |
| S09 | Дзен авторизован | Планирование статьи | Прямая загрузка через CDP и подтверждение срока |
| S10 | До срока меньше минуты | Назначение | Запрос новой даты без немедленной отправки |
| S11 | Таймаут или повтор | Возобновление | Сверка существующих объектов без слепых дублей |
| S12 | Частичный сбой | Завершение | Сохранены успехи и явный блокер по оставшейся площадке |
| S13 | Все расписания подтверждены | Завершение | «Запланировано», а не «Опубликовано» |
| S14 | Неверный канал/нет прав/истёк вход | Проверка подключения | Публикация блокируется до исправления |
| S15 | Слишком большое видео | Отправка Telegram | Ошибка, без скрытой смены формата |
| S16 | Сообщение исчезло из отложки | Проверка | Публикация требует независимого подтверждения |

Локальные тесты проверяют время, версии утверждения, повторные запуски, частичную отправку, лимиты и проверки каналов с имитацией API. Внешняя приёмка отдельно: согласованный тестовый выпуск на трёх площадках, сначала проверка отложки, затем фактического выхода. Критерий — не раньше срока, задержка до пяти минут; это не SLA внешних сервисов.
