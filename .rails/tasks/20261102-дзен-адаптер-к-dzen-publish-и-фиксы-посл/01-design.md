# Дизайн: Дзен — адаптер к dzen-publish и фиксы после реальной публикации

## Задача бизнеса
Статья Дзена должна вставать в отложку канала «Экономика не для всех!» тем же утверждённым выпуском, что YouTube и Telegram. В `main` Дзен публикуется только навыком и браузером, а CLI фиксирует лишь наблюдение (`record-browser`). В wip-ветке уже есть адаптер `tools/publishing_dzen.py`, CLI `prepare-dzen`/`schedule-dzen`/`check-dzen` и фиксы транспорта, проверенные реальной отложкой 2026-10-01 (`publish-log.md`). Переносим их на новую базу в виде «солянки»: транспорт остаётся upstream Andrrreyiv/dzen-publish, гейты наши.

## Ограничения
- База — `main`; wip и PR #12 используются как источник кода, но переносим только публикационный слой Дзена. Core-монтаж и QA рендера (`tools/render_qa.py`) не переносим.
- Для `tools/chrome_cdp.py` и `dzen-publish/ensure_cdp_chrome.ps1` берём версии из PR #12/#13 (`issue-2-auth`), а не из wip. Они новее и безопаснее: CDP только на 127.0.0.1, строгая проверка URL, режим `DZEN_CDP_MODE=external`, запрет запуска Chrome от root. Это решение зафиксировано в сравнении версий 2026-11-02.
- Внешние действия только после утверждения ревизии. Пять активных ссылок футера, порядок всех изображений и полный текст сверяются до отправки и после.
- Обычные тесты не ходят в сеть: изолированный Chromium с локальными страницами.

- Развязка с монтажом: `image_occurrences(docx)` (8 строк, wip `tools/render_qa.py`) переносится в `tools/dzen_content.py`, без `render_qa`.
- `tools/publishing_core.py`: в `revision()` добавить хеши `dzen_sequence_path`, изображений последовательности и обязательного футера (как в wip). Хуки `render_qa` из wip не переносим.
- `tools/publish_release.py`: действия `prepare-dzen`, `schedule-dzen`, `check-dzen` (как в wip, код возврата 2 для незавершённых статусов). `review-render` и `SMM_TESTING` не переносим.

Фикстуры, завязанные на `render_qa` (`tests/support.py`), заменить минимальными.

## Альтернативы
- A. Перенести wip-адаптер с минимальной развязкой от `render_qa` (выбрано). Плюсы: код проверен реальной отложкой 01.10 и BDD. Минусы: большой перенос (~1,5 тыс. строк), нужна сверка с PR.
- B. Писать адаптер заново по образцу T2/T3. Плюсы: единообразие. Минусы: теряем фиксы после реальной публикации (donation-promo, локализованные даты очереди, сравнение текста по абзацам, ленивые изображения), риск их переоткрыть на живом канале.
- C. Оставить в `main` только навык и `record-browser`. Плюсы: ничего не делать. Минусы: Дзен остаётся вне общего CLI и гейтов ревизии, хотя пользователь просил переработать все три площадки.

## Решение и обоснование
Вариант A. Самый дорогой опыт по Дзену — живая разметка редактора, и он уже вложен в wip-код. Переписывать его — значит снова платить реальными попытками на канале. Развязка с `render_qa` сохраняет правило «core не трогаем».

## Допущения и риски
- Разметка Дзена могла измениться после 01.10. Локальные тесты этого не покажут, нужна живая read-only проверка (`check-dzen` на существующей статье) с разрешения пользователя.
- Лицензии у upstream нет: риск зафиксирован в `dzen-publish/UPSTREAM.md`, решение за пользователем.
- Слияние `open_channel()` из PR с wip-версией `publish_dzen.py` может конфликтовать по навигации. Ревьюер сверяет дифф с обеими сторонами.
- Корневой `conftest.py` удаляет переменные `YOUTUBE_*`, `TELEGRAM_*`, `DZEN_*` и запрещает внешнюю сеть во всех тестах. Тесты T2/T3 должны это пережить: они офлайн, но проверить нужно.

- Идентичность изображений в редакторе и превью Дзена побайтно не доказуема: площадка перекодирует файлы. На стороне Дзена проверяются число, позиции изображений относительно текста и факт загрузки; идентичность гарантируется на входе (DOCX ↔ последовательность ↔ утверждённая ревизия). Уточнено по ревью 2026-11-02.

## Критерии приёмки
- AC-1: `prepare-dzen`/`schedule-dzen`/`check-dzen` существуют в CLI и требуют утверждённой ревизии; изменение статьи, последовательности, изображения или футера меняет ревизию — проверка: BDD `tests/bdd/test_dzen.py` (сценарии ревизии и утверждения)
- AC-2: последовательность сверяется с DOCX по тексту, числу, порядку и идентичности изображений (перестановка или подмена картинки при том же числе отклоняется); DOCX с картинками без `dzen_sequence_path` отклоняется — проверка: BDD-сценарии последовательности с двумя различимыми изображениями
- AC-3: отложка проверяется по локализованной дате очереди и авторскому превью в МСК; неверная дата не считается успехом — проверка: `test_dzen_localized_schedule_date_is_verified_exactly` + сценарии наблюдения
- AC-4: CDP только локальный (127.0.0.1/localhost, без пути, query и учётных данных), режим external не запускает Chrome — проверка: тесты `chrome_cdp` из PR (перенести в `tools/test_chrome_cdp.py` или BDD)
- AC-5: изолированный Chromium-прогон наблюдения (`test_dzen_observation.py`) проходит без внешней сети — проверка: прогон под codex-test-guard
- AC-6: core не изменён, `render_qa` не появился, тесты T1–T3 проходят с корневым `conftest.py` — проверка: `git diff main --stat` + полный прогон `tools tests/bdd`
